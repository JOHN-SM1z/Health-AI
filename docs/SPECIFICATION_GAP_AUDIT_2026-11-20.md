# Health AI technical specification implementation audit

20 November 2026, Asia/Tashkent · Specification v1.1 draft, 14 November 2026 · Current Health AI working tree

The clinic desk, kassa, queue, Mini App booking, referrals, and laboratory workflows are implemented to a substantial degree. The specification still calls for identity encryption, a shared booking agent, conversational Telegram booking, phone telephony, Rahmat payments, structured prescribing, a consultation recorder, and signed-document delivery. The previous local repair passed 1,353 tests with zero skips and 522 E2E checks across 25 workflows. The hosted database currently fails the repository's release preflight because two notification claim RPCs are missing.

The [requirement matrix](#requirement-matrix) covers every numbered functional and control requirement in the 38-page PDF. **21 implemented, 40 partial, 38 missing, 2 unverified, 1 conflict, and 1 out of scope**, across 103 requirements. Counts are by requirement, so they are not a percentage of implementation effort. “Implemented” means code or schema covers the present requirement. Where a provider or deployment is separate, the matrix calls that out.

The audit compared the PDF with the active Next.js routes and UI, application services, current migrations, tests, deployment configuration, and runbooks. It used the source checkout on `codex/clinic-operations-pilot`, with HEAD `5d7ef45fcb19e84903bbbab03020e4a2099f77cf` and local changes present. The PDF identification is SHA-256 `7cffa28624eb7d02f5f04c4498ef38356c4763dcc42a87c88d76be99fc9a0937`. Runtime checks in this pass covered the local urgency detector and read-only hosted project, migration, advisor, and function metadata. Prior test results are recorded in the [implementation status](IMPLEMENTATION_STATUS_2026-11-20.md). Vendor credentials, live delivery, clinic trials, production application revision, and actual backup operations remain unverified.

## Agent, infrastructure, and data model

The current OpenAI-compatible client creates text from a prompt. The specification requires a server-controlled state machine with typed inputs, clinic-bound authorization, per-turn confirmation before writes, and facts drawn from validated current tool output. The existing conversation inbox has assignment and urgent flags. A structured requests queue, call summary, staff outcome lifecycle, and call live board still need their own model and UI. There are 11 rows in the specification's tool table, with cancellation and rescheduling sharing a row.

Caller ID and DOB are insufficient to prove control of an existing patient's phone. ID-05 should use a verified possession challenge or another approved identity proof before linking or disclosing a card, with provisional requests or human handoff available when proof fails. Use ordinary referral authorization for the signed record only. The recorder's references to medicines and tests must be sourced mentions for the doctor to confirm. Catalogue selection, prescribing and signatures remain clinician-controlled. Reception print access requires a design that preserves the existing clinical disclosure boundary. For EV-03 retain evidence IDs, verdicts and timing, and compare encounter content in protected execution rather than putting it into logs.

The dependencies listed in the PDF include the Rahmat merchant agreement/API/sandbox/settlement format, Eskiz sender/template/callback approval, OneID agreement/scope/sandbox, clinic SIP trunk, approved speech hosting and test credentials, licensed medicine dataset, and Ministry access for national prescribing.
